存储与表格式层

本页深入讲解湖仓一体的存储底座：对象存储、开放表格式（Apache Iceberg）与元数据服务（Hive Metastore） 三件套的分工与协作，并给出 HDFS / S3 / MinIO 的选型依据、关键配置与生产调优经验。读完本页， 你将能够独立设计一个与计算引擎解耦、可被多引擎共享读写的企业级存储层。

本层定位

传统数仓（如 Teradata、Greenplum）把存储与计算耦合在同一集群，扩容时“为算力买单却买回一堆磁盘”，缩容时数据要搬家。 湖仓一体的存储层通过“对象存储 + 开放表格式 + 元数据服务”三件套实现存算分离： 计算引擎无状态、可弹性伸缩，数据以开放格式长期沉淀在廉价可扩展的存储上。

计算引擎层：Spark / Flink / Trino / Doris（无状态，可随时启停与替换）
元数据服务层：Hive Metastore / JDBC Catalog / REST Catalog（表的“电话簿”）
开放表格式层：Iceberg / Delta / Hudi（表语义、ACID 事务、快照）
物理存储层：S3 / MinIO / HDFS + Parquet 列式文件（数据的最终归宿）

对象存储 物理底座

提供近无限容量、按量计费的块级字节空间。不懂文件系统语义（没有原子 rename）， 只保证单个对象 PUT 的原子性与读到的强一致性。

开放表格式 表语义层

在文件之上定义“表”：schema、分区、事务、快照。把表元数据本身也做成存储上的开放文件， 使任何引擎都能独立读写同一张表，这是湖仓与传统数据湖的分水岭。

元数据服务 目录层

Catalog 负责回答“有哪些库表、当前有效的元数据文件是哪一个”。 它只存指针与 schema，不存数据与事务状态，因此可以随时重建或替换。

与上层引擎解耦的原理

解耦不是口号，而是四条可验证的机制。逐层向下，每一层都只依赖“开放的协议”，而不依赖任何单一引擎：

  1. 存算分离：引擎不持有数据，节点宕机/缩容不丢数据；同一份数据可同时被批、流、OLAP 引擎挂载。
  2. 开放文件格式：数据落地为 Parquet 列存，这是行业公共协议，任何新引擎都能直接解析，无需“搬家”。
  3. 自描述元数据：表结构、分区、快照全部记录在存储上的元数据文件中（如 Iceberg 的 metadata.json）， 引擎通过 Catalog 拿到入口指针即可独立读写，不依赖某个中心服务的运行状态。
  4. 提交协议标准化：事务提交 = “原子地切换元数据指针”（条件写或 Catalog 乐观锁）， 避开对象存储“无原子 rename”的硬伤，多引擎并发写同一张表也不会互相覆盖。
为什么“表格式”是分水岭：传统 Hive 表的“事务边界”其实依赖 HDFS 的原子 rename 与 NameNode 目录语义， 引擎换到对象存储后这套假设全部失效。Iceberg 等表格式把“什么是一次安全的提交”从文件系统下沉为元数据文件协议， 从此存储可以自由替换（HDFS ↔ S3 ↔ MinIO），引擎也可以自由组合——这正是本教程后续所有章节的地基。

Apache Iceberg 表格式

Apache Iceberg 由 Netflix 为解决“数 PB 级 Hive 表在日常运维中频繁出错”而设计，2020 年进入 Apache 顶级项目。 它在文件系统之上定义了一套树状元数据结构，为湖仓表带来四个核心能力：

  • ACID 每次 commit 生成一个不可变快照（snapshot），读方永远看到一致视图；写方通过乐观并发 + 冲突重试实现串行化隔离。
  • Schema 演进 安全地增列、删列、改名、调整列顺序，只改元数据、不重写数据文件；历史快照按旧 schema 依旧可读。
  • 隐藏分区 分区值由列的变换函数（days / bucket / truncate）自动推导，用户与数据无需感知分区列。
  • 时间旅行 任意历史快照可重复查询，天然支撑审计、回滚与增量消费。

元数据树：metadata.json → snapshot → manifest → data file

Iceberg 的一切能力都源于这棵“自描述”的元数据树。读写双方只需约定入口（当前 metadata.json），其余全部按文件指针逐级展开：

  1. metadata.json：表入口文件，记录表 UUID、当前 schema、分区规格、属性与快照列表； 文件名自带版本号（00001-xxxx.metadata.json），提交即产生新版本。
  2. snapshot：一次成功提交的不可变快照，包含操作类型（append / overwrite / delete）、 指向 manifest-list 的指针与汇总统计（added-files、total-records 等）。
  3. manifest-list / manifest：清单文件（Avro）逐条记录数据文件路径、分区值与 min/max/null 统计，是分区裁剪与文件级跳过的物理依据。
  4. data file：真正的 Parquet/ORC/Avro 数据文件，文件名含分布式唯一 ID，永不覆盖重写。
为什么读性能好：查询引擎先在 manifest 上用分区值与 min/max 统计做“文件级索引过滤”， 绝大多数不符合条件的数据文件根本不会被打开。这套统计随写入自动维护，不需要额外构建索引服务。

隐藏分区 vs Hive 分区

维度 Hive 分区 Iceberg 隐藏分区
分区列 必须是表中冗余存储的物理列（如 dt string） 任意列的变换：days(ts)、bucket(16, user_id)、truncate(10, city)，无需冗余列
分区值来源 写入方手工指定，写错分区无人拦截（经典事故源） 引擎按 transform 自动推导，结构上不可能写错分区
分区演进 改分区结构 = 重建表 + 全量重写历史数据 分区规格可演进，新旧规格在同一张表共存
查询体验 用户必须感知分区列并在 SQL 里写出过滤条件 对 ts > '2026-11-01' 的过滤被自动换算成分区裁剪
列裁剪友好度 冗余列占存储且容易与源列不一致 单一事实来源，无冗余

Spark 建表：分区、排序与写入属性

-- 完整建表：隐藏分区 + 目标文件大小 + 压缩与元数据治理属性
CREATE TABLE lakehouse.dws_orders (
  order_id     BIGINT,
  user_id      STRING,
  city         STRING,
  order_amount DECIMAL(12, 2),
  order_ts     TIMESTAMP          -- 不需要冗余 dt 列，分区由变换推导
) USING iceberg
PARTITIONED BY (days(order_ts))               -- 隐藏分区：按天，自动裁剪
TBLPROPERTIES (
  'format-version'                     = '2',           -- v2 支持行级删除（MERGE/删除必需）
  'write.format.default'               = 'parquet',
  'write.target-file-size-bytes'       = '268435456',   -- 目标文件 256MB，防小文件
  'write.parquet.compression-codec'    = 'zstd',
  'write.parquet.row-group-size-bytes' = '134217728',   -- 行组 128MB
  'write.distribution-mode'            = 'hash',        -- 写入按分区键 shuffle，减少每任务小文件
  'write.metadata.previous-versions-max'        = '100',
  'write.metadata.delete-after-commit.enabled'  = 'true' -- 自动清理过期 metadata.json
);

-- 数据按时间聚簇（Z-Order/排序），提升范围扫描时文件级跳过命中率
ALTER TABLE lakehouse.dws_orders WRITE ORDERED BY (order_ts);

-- 需要按用户打散时可用多列排序，兼顾多种查询模式
ALTER TABLE lakehouse.dws_orders WRITE ORDERED BY (city, order_ts);

MERGE INTO：行级更新与打宽

-- 以订单号为主键：迟到更新覆盖、删除标记生效、新单插入，一次提交完成
MERGE INTO lakehouse.dws_orders t
USING (
  SELECT * FROM lakehouse.stg_orders
  WHERE etl_date = current_date()
) s
ON t.order_id = s.order_id
WHEN MATCHED AND s.op_type = 'D' THEN DELETE
WHEN MATCHED THEN UPDATE SET
  t.order_amount = s.order_amount,
  t.order_ts     = s.order_ts,
  t.city         = s.city
WHEN NOT MATCHED THEN INSERT (
  order_id, user_id, city, order_amount, order_ts
) VALUES (
  s.order_id, s.user_id, s.city, s.order_amount, s.order_ts
);

-- 执行计划验证：确认走了“重写受影响文件 + 删除文件”而非全表重写
EXPLAIN MERGE INTO lakehouse.dws_orders t USING lakehouse.stg_orders s
ON t.order_id = s.order_id WHEN MATCHED THEN UPDATE SET *;

时间旅行 ≠ 无限回滚：历史快照依赖未被清理的数据文件。生产表必须配置快照过期策略 （expire_snapshots，见下文调优一节），否则 metadata.json、manifest 与已逻辑删除的数据文件会无限累积， 最终拖垮所有引擎的 planning 阶段。

HDFS 分布式文件系统

尽管对象存储已成湖仓首选，HDFS 仍是大量存量私有机房的中坚。理解它的架构，也有助于理解对象存储“放弃”了哪些能力。

NameNode / DataNode 架构

  • NameNode（主）：维护文件系统命名空间（目录树、块映射）于内存，持久化为 FSImage + EditLog； 是整个集群的单一元数据中心——也是小文件问题的根源（每个文件/目录/块约占数百字节内存）。
  • DataNode（从）：存储实际数据块，定期心跳与块报告（BlockReport）给 NameNode，负责块的读写与副本流水线复制。
  • 高可用：JournalNode 组成的共享 EditLog + Active/Standby 双 NameNode + ZKFC 自动故障切换， 避免单点瘫痪；SecondaryNameNode 只做镜像合并，不是热备。

块、副本与机架感知

文件被切分为固定大小的块（默认 128MB），每块默认 3 副本。副本放置由机架感知策略决定： 第 1 副本写客户端本节点（或随机），第 2 副本放到另一机架，第 3 副本与第 2 副本同机架不同节点—— 在“整个机架掉电”与“跨机架网络带宽”之间取得平衡。DataNode 启动时通过拓扑脚本上报机架位置：

<!-- core-site.xml：机架感知脚本（返回形如 /rack01 的机架路径） -->
<property>
  <name>net.topology.script.file.name</name>
  <value>/etc/hadoop/conf/rack-topology.sh</value>
</property>

关键参数

<!-- hdfs-site.xml：与湖仓负载最相关的参数 -->
<property>
  <name>dfs.replication</name>
  <value>3</value>                    <!-- 生产默认 3；归档冷表可降 2 或转纠删码 -->
</property>
<property>
  <name>dfs.blocksize</name>
  <value>268435456</value>            <!-- 256MB：湖仓大文件顺序扫描，减少块数与 NN 压力 -->
</property>
<property>
  <name>dfs.namenode.handler.count</name>
  <value>64</value>                   <!-- RPC 服务线程，重负载/多引擎并发时加大 -->
</property>
<property>
  <name>dfs.datanode.failed.volumes.tolerated</name>
  <value>1</value>                    <!-- 允许 1 块盘损坏不掉节点 -->
</property>

  <name>dfs.client.read.shortcircuit</name>
  <value>true</value>                <!-- 计算与存储同置时启用短路读，绕过 TCP -->

适用场景：自建机房且计算存储同置追求极致吞吐（短路读 + 本地副本优先）、已有 Hadoop 生态与运维体系、 对数据主权要求高无法上公有云。反之，公有云上优先对象存储，多云/混合架构则用 MinIO 对齐 S3 协议。
HDFS 小文件是 NameNode 的内存杀手：1 亿个小文件即可能吃掉数十 GB 堆内存并让启动回放 EditLog 长达小时级。 湖仓表写入务必控制 target-file-size-bytes，并对历史小文件执行 compaction 合并。

S3/MinIO 对象存储

对象存储把“文件系统”简化为“键值空间”：key 即路径，value 即不可变对象。它用极简的语义换取了近乎无限的扩展性与极低成本， 但也正是这层“简化”，逼出了 Iceberg 元数据协议的设计。

对象存储 vs HDFS

维度 HDFS S3 / MinIO 对象存储
成本 3 副本 ×1 容量 = 3 倍占用，含硬件折旧与专人运维 纠删码约 1.2–1.5 倍冗余；公有云按量计费、可生命周期转冷归档
扩展性 受 NameNode 内存上限制约（亿级对象需 Federation） 去中心化，近无限；扩容只是加节点/加盘
读性能 顺序/随机均好，短路读可达本地盘水平 首字节延迟高（几十~几百 ms），顺序吞吐大对象后可跑满带宽
一致性 / 原子性 rename 原子、目录原子可见，经典 Hive 提交依赖它 单对象 PUT 强一致；无原子 rename，LIST 非快照语义
运维 机架规划、坏盘更换、NN HA 自担 S3 全托管；MinIO 轻量自运维
湖仓适配 传统 Hadoop 生态良好 Iceberg/Delta/Hudi 均原生适配，是湖仓事实标准底座

S3 的一致性短板与 Iceberg 的规避方式

经典的 Hive 提交协议是“写临时目录 → 原子 rename 到正式路径”。在 S3 上这条路径全面失效：

  • rename = COPY + DELETE，非原子且昂贵（GB 级目录重命名要以小时计）；
  • LIST 不是快照：分页枚举期间桶内在变化，无法作为“提交完成”的判定依据；
  • 提交一半失败会留下“半张表”，读取方无从分辨。

Iceberg 的规避方式恰恰是把提交从“动数据”改为“动指针”：

  1. 数据文件以分布式唯一 ID 命名，直接写入最终目录，永不重命名；文件不可变，先写后登记天然安全；
  2. 提交时生成新的 manifest 与 snapshot，最后原子 PUT 一个新的 metadata.json （S3 单对象写是强一致的），或通过 HMS/JDBC/REST Catalog 的乐观锁切换指针；
  3. 读取方从 Catalog 拿到确定的 metadata.json 入口，完全不需要 LIST 目录，也不依赖 rename；
  4. 失败提交残留的“孤儿文件”由 remove_orphan_files 定期回收，不影响正确性。

S3A Commiter 配置

当 Spark 以原生 DataSource 方式（非 Iceberg 表）直接写 Parquet 到 S3 时，仍需 S3A 提交器来避免 “_temporary 目录 + rename 提交”陷阱。Iceberg 表自身不需要 rename，但集群级配置通常一并开启：

# spark-defaults.conf：magic committer（零 rename，通过隐藏目录 + _SUCCESS 标记提交）
spark.hadoop.fs.s3a.committer.name=magic
spark.hadoop.fs.s3a.committer.magic.enabled=true
spark.hadoop.mapreduce.outputcommitter.factory.scheme.s3a=org.apache.hadoop.fs.s3a.commit.magic.MagicCommitterFactory
spark.sql.sources.commitProtocolClass=org.apache.spark.sql.execution.datasources.SQLHadoopMapReduceCommitProtocol

# 或 directory committer（任务直接写目标目录，driver 最后汇总提交）
spark.hadoop.fs.s3a.committer.name=directory
spark.hadoop.fs.s3a.committer.directory.summary=true
spark.hadoop.mapreduce.outputcommitter.factory.scheme.s3a=org.apache.hadoop.fs.s3a.commit.directory.DirectoryCommitterFactory

# 大表写入吞吐：分块并行上传与连接池
spark.hadoop.fs.s3a.fast.upload=true
spark.hadoop.fs.s3a.threads.max=32
spark.hadoop.fs.s3a.connection.maximum=200
spark.hadoop.fs.s3a.block.size=64M          # 分块上传块大小

MinIO：私有化的 S3

MinIO 以 S3 兼容 API + 纠删码（Erasure Coding）+ Bitrot 校验著称，是私有机房/边缘环境落湖仓的首选底座。

# 单机体验：一条命令拉起对象存储 + Web 控制台
docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  -v /data/minio:/data \
  -e MINIO_ROOT_USER=lakehouse \
  -e MINIO_ROOT_PASSWORD='Lakehouse#2026' \
  minio/minio server /data --console-address ":9001"

# 生产分布式：4 节点 x 4 盘纠删码（分布式模式至少 4 节点）
# 在每个节点执行相同命令，主机名用 {1...4} 展开语法
export MINIO_ROOT_USER=lakehouse
export MINIO_ROOT_PASSWORD='Lakehouse#2026'
minio server http://minio{1...4}.lakehouse.local/data{1...4}
  • 纠删码：默认 EC:4（4 数据 + 4 校验），空间利用率远高于 3 副本，可按桶调整；
  • 部署要点：节点间时间同步（NTP）必须严格；生产建议 TLS 与独立域名；分布式模式扩容需按“纠删组”整组扩展；
  • 定位：与公有云 S3 协议对齐后，开发测试用 MinIO、生产上 S3 的迁移基本只改 endpoint 与凭证。
最佳实践：统一用 s3a:// scheme + path-style access 访问 MinIO； 引擎侧 endpoint / AK / SK 全部走配置中心或环境变量，严禁写死在 SQL 与代码仓库里（防止凭证泄漏进 Git）。

Hive Metastore 元数据服务

湖仓多引擎的“表清单”需要一个中立裁判：Spark、Flink、Trino、Doris 各自的 catalog 互不相通， Hive Metastore（HMS）以 Thrift 服务的形式提供了跨引擎的共享目录——谁都能问它“库表清单、schema、存储位置”。

多引擎共享元数据

引擎 接入方式（示例） 典型用途
Spark spark.sql.catalog.lakehouse.type=hive 批处理读写 Iceberg 表，元数据与 Flink/Trino 完全一致
Flink CREATE CATALOG ... 'catalog-type'='hive' 流式写入/增量消费同一批表
Trino iceberg.properties：iceberg.catalog.type=hive_metastore 交互式联邦查询，直读 Parquet
Doris / StarRocks CREATE EXTERNAL CATALOG ... TYPE=iceberg 湖上极速查询与湖仓联邦

能力边界：HMS 只管“户口本”

HMS 有什么：库/表/分区清单、列 schema、存储 location、SerDe 参数等静态描述信息， 外加基于心跳的粗粒度锁接口。
HMS 没有什么：没有事务日志、没有快照链、没有表级统计信息。Iceberg 表在 HMS 里只是 “一个指向 metadata.json 的指针”，ACID 与时间旅行完全由表格式自身的元数据文件实现—— 引擎绝不能只看 HMS 的表结构就断定数据状态。

关键配置

<!-- hive-site.xml：Metastore 服务端核心参数 -->
<property>
  <name>hive.metastore.uris</name>
  <value>thrift://hms1.lakehouse.local:9083,thrift://hms2.lakehouse.local:9083</value>
  <!-- 客户端可配多个地址轮询容灾 -->
</property>
<property>
  <name>hive.metastore.server.max.threads</name>
  <value>200</value>                <!-- 多引擎高并发时的 RPC 线程池 -->
</property>
<property>
  <name>hive.metastore.pool.max.active</name>
  <value>32</value>                 <!-- 底层 JDBC 连接池上限 -->
</property>
<property>
  <name>hive.metastore.metrics.enabled</name>
  <value>true</value>              <!-- 暴露 RPC/JMX 指标，接入监控 -->
</property>

HMS 瓶颈与解耦建议

  • 瓶颈表现：所有引擎的 DDL 与首查都要过 HMS，高峰期 RPC 排队；Thrift 单实例能力有限， 底层数据库连接池打满后表现为“建表/查询 list 偶发超时”。
  • 解耦路径一：Catalog 多实例：HMS 无状态化部署多实例（共享后端数据库）+ 负载均衡，按引擎划分访问组。
  • 解耦路径二：换更轻的 Catalog：Iceberg 支持 JDBC Catalog（元数据表放 PostgreSQL/MySQL）、 REST Catalog（Nessie / Polaris / Gravitino 等），把“表清单”从 Hadoop 体系解放出来：
# Spark 挂载 Iceberg JDBC Catalog：不再依赖 HMS
spark.sql.catalog.lakehouse=org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.lakehouse.catalog-impl=org.apache.iceberg.jdbc.JdbcCatalog
spark.sql.catalog.lakehouse.uri=jdbc:postgresql://pg.lakehouse.local:5432/iceberg
spark.sql.catalog.lakehouse.jdbc.user=iceberg
spark.sql.catalog.lakehouse.jdbc.password=******
spark.sql.catalog.lakehouse.warehouse=s3a://lakehouse/warehouse
生产经验：存量 HMS 不必推倒重建。推荐演进路线：新湖仓区用 REST/JDBC Catalog 承接增量表， 老表继续经 HMS 访问，两边通过同一套 warehouse 路径规范兼容；等 Iceberg REST Catalog 标准稳定后再统一收口。

存储层调优要点

存储层的性能问题 90% 落在四个字上：小文件、坏布局。以下四项是投产前必须规划的内容。

1. 文件大小规划

平均文件大小 典型后果 处置
< 32MB planning 变慢、对象存储请求放大、NameNode 内存膨胀 调大 write.target-file-size-bytes；开启 write.distribution-mode=hash；执行 compaction
128MB–512MB 对象存储/列存扫过的黄金区间 维持：目标 256MB，配合 128MB 行组
> 1GB 单文件读取时间过长，任务尾部拖死；细粒度裁剪失效 调小 target；重写时按排序键拆分

2. Parquet 行组与压缩

-- 行组：列存的最小读取单元，建议 128MB–256MB，与扫描列宽匹配
ALTER TABLE lakehouse.dws_orders SET TBLPROPERTIES (
  'write.parquet.compression-codec'    = 'zstd',        -- 压缩比与解压速度的平衡点
  'write.parquet.compression-level'    = '3',           -- 1-22，越大越慢但更省
  'write.parquet.row-group-size-bytes' = '268435456',
  'write.parquet.page-size-bytes'      = '1048576'      -- 页是编码/统计最小单元
);
  • 宽表点查场景（只取少数列）可适当减小行组，让“读到的无用数据”更少；
  • snappy 解压最快、zstd 综合最优、gzip 只用于超冷归档；
  • 查询侧确保 spark.sql.parquet.filterPushdown=true（默认开），让 min/max 谓词下推到行组。

3. 分区设计原则

  1. 用天然高频过滤列：分区列必须出现在绝大多数查询的 WHERE 中，否则分区只是负担；
  2. 基数适中：单表分区数建议控制在数千到数万级；按天分区足够就不要按小时；
  3. 优先隐藏分区 transform：days(ts) / months(ts) / bucket(64, user_id)， 免冗余列、免手工指定；
  4. 预估文件数：每日写入文件数 ≈ 分区数 × 每分区写入任务数，反推 target-file-size 是否合理。

4. 元数据爆炸治理

流式写入 = 高频提交 = 快照与 manifest 指数级累积。治理三件套必须进调度系统：

-- ① 快照过期：只保留最近 7 天 + 至少 100 个快照
CALL lakehouse.system.expire_snapshots(
  table => 'lakehouse.dws_orders',
  older_than => TIMESTAMP '2026-10-29 00:00:00',
  retain_last => 100
);

-- ② manifest 合并：大量小 manifest 会拖慢 planning
CALL lakehouse.system.rewrite_manifests(
  table => 'lakehouse.dws_orders'
);

-- ③ 孤儿文件清理：回收失败提交残留（低峰期执行，需引擎独占写）
CALL lakehouse.system.remove_orphan_files(
  table => 'lakehouse.dws_orders',
  older_than => TIMESTAMP '2026-11-04 00:00:00'
);

配合表属性做“写入时自愈”，避免依赖人工：

ALTER TABLE lakehouse.dws_orders SET TBLPROPERTIES (
  'write.metadata.previous-versions-max'       = '100',   -- metadata.json 最多留 100 版
  'write.metadata.delete-after-commit.enabled' = 'true',  -- 提交后自动删过期入口文件
  'write.metadata.metrics.default'             = 'truncate(16)', -- 长字符串统计截断，瘦身 manifest
  'commit.manifest.target-size-bytes'          = '8388608',     -- manifest 自动合并目标 8MB
  'commit.manifest.min-count-to-merge'         = '100'
);
生产经验总结： 目标文件 256MB + 行组 128MB + zstd；分区用 days() 且单表 ≤ 1 万个分区； 流表快照保留 7 天、离线表 30 天；compaction / expire / rewrite_manifests / remove_orphan_files 四个维护动作全部进调度并在低峰执行；上线前先用真实流量做一周“文件数与 planning 耗时”观测，再定稿参数。

适用边界

湖仓表不是银弹。以下场景，传统数仓或 OLAP 引擎原生表依然是更优解：

场景特征 推荐方案 原因
毫秒~百毫秒级点查、高 QPS 在线服务 ClickHouse / HBase / Redis 对象存储首字节延迟 + planning 开销无法满足在线 SLA
秒级频繁小事务更新且要求即时可见 数仓原生表（如 Doris 内表） Iceberg 提交成本（新 manifest/snapshot）决定高频微批不经济
超高并发低延迟聚合（实时大屏） ClickHouse / Doris / StarRocks 内表 预聚合 + 向量化执行 + 索引，湖仓表按需扫描天然吃亏
GB 级以下小数据集、强事务 OLTP MySQL / PostgreSQL 事务与并发控制能力完全不同层级
PB 级批处理、机器学习训练、多引擎共享 湖仓表（Iceberg） 开放格式 + 存算分离 + 时间旅行的主场

一个实用的判断口诀：“给机器反复扫的，放湖仓；给人实时看的，放 OLAP；给业务改的，放 OLTP”。 湖仓与这些引擎之间再通过联邦查询（见查询层一章）打通，形成互补贴而非互替代的组合。
