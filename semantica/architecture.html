Architecture

Semantica 架构设计

从浏览器到 Neo4j：系统由哪些组件构成、数据怎样流动、关键取舍为什么这样定。

分支 semantica-system MCP 修订号 6 · 精简档 16 工具 两台服务器均已切换 Neo4j 主库

版本：2026-11-06（对应代码分支 semantica-system，MCP 修订号 6，两台服务器均已切换 Neo4j 为主库） 依据：semantica/docs/ 00–12 系列文档整理。细节以原文档为准，本文是面向开发与架构评审的综合说明。

1. 系统概述

Semantica 是一套团队级语义知识图谱系统，围绕一张共享的知识图谱，为三类使用者提供服务：

使用者途径做什么
团队成员（人）浏览器 → Explorer 界面浏览图谱、搜索、推理、SPARQL/Cypher 查询、本体管理、决策因果分析
数据工程师JupyterLab（lab 容器）写 Python 做文档抽取、数据库接入实验，把结果推入图谱
智能体 / 外部程序MCP 协议（/mcp 端点）用 16 个工具检索、统计、写入图谱，走完数据库接入全流程

核心设计原则：

  • 不改上游源码：上游 Semantica 0.7.0（提交 52f34f0，MIT 协议）的 src/ 保持原样，所有定制以"启动包装、构建期补丁、独立侧车"三种形式叠加，方便升级。
  • 图谱放在硬盘上的 Neo4j（2026-11-03 起）：摆脱"整张图在 Explorer 进程内存里"的规模与持久化限制；Explorer 界面变为定期刷新的只读副本。
  • 智能体只能经 MCP 侧车进入：独立的 Bearer 令牌域、限流、审计、可一键停用，与人的 Basic Auth 凭据完全隔离。

3. 组件详解

3.1 网关 semantica-gateway

nginx:alpine 单文件模板（deploy/nginx/default.conf.template），启动时替换 ${SEMANTICA_API_KEY}。

对外端口后端规则要点
18835（:80）explorer:8000Basic Auth（团队共用账号 semantica）；剥掉客户端 Authorization、统一附加 X-API-Key；WebSocket 升级；请求体 ≤ 60 MB；超时 3600 s；/api/health 免登录
18835 location = /mcpmcp:8001不走 Basic：Authorization: Bearer 原样转发；清掉 X-API-Key；按来源限流 20 r/s、突发 40；请求体 ≤ 1 MB；超时 300 s；413/429/502–504 回 JSON
18836（:81）lab:8888Basic Auth；上传 ≤ 1 GB；超时 86400 s

设计动机（D7、D19）：浏览器接触不到 API Key；MCP 客户端是机器身份，用独立 Bearer 令牌域，避免往共用 .htpasswd 加账号（那会同时给出去 REST 全量写入和 JupyterLab 代码执行权限）。resolver 127.0.0.11 让后端重启期间网关照常返回 502 而不是自己挂掉。

3.2 semantica-explorer（界面 + 主 API）

  • 上游：FastAPI + uvicorn（:8000），前端 React（Vite 构建），图和状态原本只在内存。
  • 持久化包装（deploy/app/explorer_persistent.py，决策 D5）：不改上游源码，启动前读盘建 GraphSession 再调 create_app()；运行中每 30 秒按指纹原子写盘（临时文件 + fsync + os.replace）；每小时快照一份（保留 48 份）；停止时 stop_grace_period: 60s 内强制存盘。graph.json 读不出来就拒绝启动（提示从快照恢复）。
  • 部署专用接口 /api/seed（seed_routes.py）：上游对记忆、溯源、本体版本没有 HTTP 写入口，示例数据导入程序经此写入，需 X-API-Key，幂等。
  • 前端汉化（deploy/l10n/，决策 D9）：构建期在副本上打补丁 + 用 TypeScript 编译器 API 做词条替换（约 1200 条 zh-CN 词典），加运行时兜底 zh-runtime.js；产物只读挂载进容器（D10），改界面只需同步文件重启容器。
  • 只读副本模式（D28）：SEMANTICA_READ_ONLY=1 时写接口按"方法 + 路径"白名单拒绝（403 中性提示），由 deploy/neo4j/replica-refresh.sh 以"导出 → 试启动 → 停副本换文件 → 核对"四步从 Neo4j 刷新（每次约 6 秒 502）。

3.3 semantica-lab（JupyterLab）

  • JupyterLab 4.6.4 中文界面，161 个附加包（openai、instructor、python-docx、pdfplumber、SQLAlchemy 等），内存 16 GB / 16 核，全团队共用。
  • 环境变量注入密钥（OPENAI_API_KEY、SEMANTICA_API_KEY 等），用户代码里不出现密钥。
  • 辅助模块 semantica_lab：read_text / extract / payload_from_extraction / payload_from_graph / push / stats，封装"读文档 → 大模型抽取 → 推入图谱"流水线；含长文分段、推理模型思考开关处理（install_openai_defaults() 给 openai SDK 打类级补丁）。
  • 安全边界：非 root 运行、不挂 docker.sock、可写挂载只有 workspace；Jupyter 自带 token 关闭，靠网关 Basic Auth 保护。

3.4 semantica-mcp（MCP 侧车）

智能体接入的唯一通道，独立容器（决策 D16），核心职责：MCP 协议适配、面向大模型的工具语义、鉴权 / 限流 / 审计、对 Explorer 的保护。

  • 协议：MCP Streamable HTTP 的无状态子集——只收 POST、只回 JSON、GET 回 405、不发会话 id、拒绝批量；协商版本 2025-06-18（也接受 2025-03-26、2024-11-05，新版客户端可协商出 2025-06-18）。按 AgentScope 的 MCP Java SDK 0.17.2 实测行为定制。
  • 鉴权：Authorization: Bearer <令牌>，与 clients.json（只存 sha256，热加载）里逐条 hmac.compare_digest 比对。明文令牌只存在于宿主机 mcp-secrets/（不挂进任何容器）和 AgentScope Vault。
  • 角色与档位：角色 reader / editor；现行唯一对外目录是精简档（compact）16 个工具（读 11、写 5），由 native 档 38 个工具按"重叠的合并、不重叠的分开"派生，只转发不重写（安全检查、写入限频、审计、溯源都在 native 实现里）。说明文字从约 3.2 万字压到约 1.7 万字，每轮对话首请求输入约 17,250 → 约 12,900 token。
  • 双后端（D24，修订号 4 起）：MCP_BACKENDS 同时提供 Explorer 后端（REST + WS，建派生索引）和 Neo4j 后端（Bolt 直查，不建索引），按 clients.json 的 backend 字段为每个客户端选择；未启用的后端返回 503，不悄悄回退。两台服务器现网均只用 Neo4j 后端（sparql_query 相应换成只读 cypher_query）。
  • 派生索引新鲜度（D18，仅 Explorer 后端）：代际计数驱动失效——WS 变更事件、WS 重连、15 秒 stats 指纹轮询、60 秒最大年龄；读时单飞重建、读者最多等 3 秒；按类型分页拉节点把构建代价从 O(N²/页) 降到 O(N)。
  • 对 Explorer 的保护：到 Explorer 并发 6、SPARQL 并发 2、重型工具并发 1；每客户端每分钟 120 次调用；单次结果 2 万字符截断；SPARQL 拒绝 SERVICE / FROM（防 SSRF，D21）；规则推理先在侧车估算计算量，超限不交给 Explorer。
  • 容器加固：只读根文件系统（仅 64 MB /tmp 可写）、去全部 capability、no-new-privileges、不发布端口、不挂数据目录；内存 1 GB / 2 核（实际约 100–120 MiB）。
  • 一键停用：停用某客户端（1 秒内 403）、隐藏某工具（tools.override.json）、disabled 开关文件关停整个 MCP（立即 503），均不用重启。

3.5 semantica-neo4j（图数据库主库）

  • Neo4j 2025.03.0 社区版，独立 compose 项目（deploy/neo4j/），堆 1–2 GB、页缓存 1 GB、容器内存 4 GB，1000:1000 运行，no-new-privileges，宿主端口只监听 127.0.0.1。
  • 数据模型（D25）：graph.json 的节点 → (:Entity:<类型>)，关系 → -[:<关系名>]->，state.json 的 7 个分区 → (:SemanticaMeta:WorkspaceItem)；每条记录的 _raw 存 Explorer REST 记录原样，辅助属性用派生索引的同一批函数算出——保证工具输出与 Explorer 后端逐项一致（A/B 验证），且能导出回 Explorer 自己的文件格式。
  • 主库标记：GraphMeta.system_of_record（69 与阿里云现均为 neo4j）。写入仅在 MCP_NEO4J_WRITES 打开且 Neo4j 是主库时允许；一次调用的全部写入在一个事务里提交。
  • 只读 cypher_query（D26）：静态检查 + EXPLAIN 预检 + READ 事务三层防护，替代 SPARQL（社区版没有只读用户，内置过程在只读事务里也能调用，故需多层防护）。
  • 溯源不进 Neo4j（D27）：仍是上游 ProvenanceManager 管理的 SQLite，Neo4j 为主库时由写入端（MCP 侧车、接入写入作业）独占，fcntl 文件锁串行化。
  • 迁移与核对：python -m semantica_mcpd.graphdb.migrate bundle|load|verify|status|reset、graphdb.export；69 上经 deploy/neo4j/graphdb.sh 在一次性容器里跑。

3.6 AgentScope（合同专家智能体）

  • AgentScope Java 2.0.4（构建与部署在 agentscope2-java-test/、aliyun/agentscope/），控制台 http://10.100.0.69:18180。
  • 现行智能体：69「合同专家」（Agent semantica-native，精简档模板 agent-compact.json）、阿里云 contract-expert；模型 GLM-5.3。
  • 令牌注入：Vault 里的 static_bearer 凭据（target = MCP 服务名 semantica）自动给 /mcp 请求加 Authorization: Bearer；Agent 定义里不写任何占位符。Vault 必须与 Agent 同命名空间。
  • 16 个工具全部 always_allow（控制台 Chat 页没有审批界面，always_ask 会把回合挂死）；内置工具保留、禁用 bash/write/edit。

3.7 数据接入（automap / CLM）

  • 关系数据库 → 图谱的自动映射流水线：semantica.ingest.DBIngestor 只读连接源库 → 大模型生成映射（表 → 类、列 → 属性、外键 → 关系）→ 演练（dryrun）→ 人工审核意见 → 导入（push）。
  • 执行器 deploy/integrations/automap/onboard_runner.py 经 spool 目录与 MCP 侧车通信；智能体用 database_onboarding 工具即可发起、续跑（resume_job_id，湖仓合同从头约 1 小时 → 续跑 15–25 秒）、带审核意见（review_edits）、取消。
  • 湖仓链路（DataX）：69 的真实合同数据（25,690 实体 / 56,123 关系）即由此导入。

5. 数据架构与数据流

【写入路径】
关系数据库/湖仓 ──automap(DBIngestor+LLM 映射+演练+审核)──► Neo4j 主库（一个事务提交，修订号+1）
智能体 write_entity / add_relationship / write_decision ──► MCP 侧车 ──► Neo4j 主库
JupyterLab 实验（lab.push）──► Explorer REST ──►（69 已切主库，实验数据走 Neo4j 写入链路）

【读取路径】
浏览器 ──► 网关 ──► Explorer（只读副本，replica-refresh.sh 定期从 Neo4j 刷新，约 6 秒 502/次）
智能体 ──► 网关 /mcp ──► MCP 侧车 ──► Bolt ──► Neo4j 主库（cypher_query 等只读查询）

【溯源】
写入端独占 provenance SQLite（fcntl 锁）；Explorer 副本用自己的副本文件
  • 目录布局：代码根（/mnt/llm/semantica，与仓库同步）与状态根（/mnt/llm/semantica-data，不同步、升级不删）分离（D6）；密钥全部在状态根（600/700 权限），不进仓库。
  • 一致性：Neo4j 后端与 Explorer 后端的工具输出逐字比较测试 + 真实数据 A/B；有意的差异逐条登记。
  • 备份：Explorer 每小时快照（48 份轮换）+ 图谱与溯源库分别备份；Neo4j 主库整库恢复不能用 reset + load，另有专门步骤（12 §12）。

6. 关键设计决策摘要

#决策一句话理由
D5持久化用启动包装，不改上游源码src/ 保持原样，方便升级；代价是依赖上游内部名字
D8全团队一张图，按实验名分命名空间协作简单；上游无删点接口，清理只能整图重置
D16智能体接入用独立 MCP 侧车容器上线/回滚不动 Explorer；MCP 故障不影响界面与存盘
D17协议用 Streamable HTTP 无状态子集匹配 AgentScope Java 客户端实测行为；服务重启不用重连
D19MCP 用独立 Bearer 凭据域机器身份与人的 Basic 账号隔离；令牌只在 /mcp 有效
D23图谱放入硬盘上的 Neo4j，MCP 直查摆脱内存规模限制（湖仓 56,340 条关系已超上游 SPARQL 5 万上限）
D24一个侧车双后端，按客户端选择工具规格只有一份，可在同进程逐项 A/B，切换只改配置
D25_raw 存原样记录 + 派生函数算辅助属性输出与 Explorer 后端逐项一致，又能导回 Explorer 格式
D26只读 cypher_query 三层防护社区版没有只读用户，内置过程需事务层拦截
D27溯源不进 Neo4j，仍是 SQLite沿用上游记录格式与哈希链；副本可直接读同种文件
D28Neo4j 主库时 Explorer 只读副本汉化界面原样可用；上游新增写接口也拦得住
D29Neo4j 写入双重开关（环境变量 + 主库标记）防止往副本里写数据导致两边不一致

7. 已知限制与演进路线

当前限制

  • Explorer 界面上的智能体写入要等下次副本刷新才可见；界面写按钮可见但点了只得到中性提示。
  • 关系写进去不能删除（上游限制）；删除实体即"归档"，可恢复。
  • Neo4j 后端简单查找比内存索引慢（几十毫秒对几毫秒；find_paths 中位数约 0.36 秒）。
  • 共用 Basic 账号，无法按人审计界面操作；REST /api/sparql 的 SERVICE 拦截在第三期才做。
  • 图超 20 万节点 / 50 万关系时（Explorer 后端）派生索引工具回退 REST。

演进路线

  • 第一期（已上线）：只读 MCP。
  • 第二期（部分已随 native/compact 档上线）：写入工具、维护助手。
  • 第三期（计划）：Explorer 加固——REST 拦 SERVICE、SPARQL 与推理可中止、可选 revision 接口（需一次 Explorer 重启窗口）。
